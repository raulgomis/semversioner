# Semversioner

**Release automation for AI-native software delivery.**

Semversioner turns every code change into structured release intent, then gives your CI/CD pipeline everything it needs to calculate versions, generate changelogs, and publish releases automatically.

It is designed for modern delivery workflows where humans and AI coding agents contribute continuously, and releases need to remain predictable, auditable, and safe.

[![PyPI Version](https://img.shields.io/pypi/v/semversioner.svg)](https://pypi.org/project/semversioner/)

## AI-native delivery needs deterministic releases

AI coding agents can generate, review, and merge changes faster than traditional release processes can manage them. The bottleneck moves from writing code to understanding what changed, deciding the next version, documenting the release, and publishing it safely.

Semversioner makes release intent part of every change.

Each pull request contributes a small, machine-readable changeset describing:

- whether the change is a `major`, `minor`, or `patch`
- what changed
- optional metadata such as pull request IDs, issue IDs, agents, models, teams, or components

Your CI/CD pipeline can then aggregate those changesets and fully automate the release process.

```text
Human or AI agent
        │
        ▼
Code change + Semversioner changeset
        │
        ▼
Pull request validation
        │
        ▼
Merge to main
        │
        ▼
Version calculation
        │
        ▼
Changelog generation
        │
        ▼
Build, publish, tag, and deploy
```

## Why Semversioner for AI-native CI/CD?

### Deterministic versioning

Version decisions are based on explicit changesets committed with the code, not commit-message conventions, branch names, or an AI model interpreting the repository after the fact.

### Safe autonomous releases

AI agents can propose changes and release intent, while CI validates that every meaningful change includes the information required for a safe release.

### Fully automated delivery

On merge, your pipeline can calculate the next version, generate release notes, build artifacts, publish packages or images, create tags, and deploy without manual release coordination.

### Auditable by design

Every release can be traced back to the individual changesets that created it. This makes automated delivery easier to review, debug, and govern.

### Works across delivery platforms

Semversioner is independent of any CI/CD provider. It can be used with GitHub Actions, Bitbucket Pipelines, GitLab CI, CircleCI, Jenkins, Buildkite, or any system that can run a CLI command.

### Designed for parallel contribution

Each pull request owns its own changeset. Multiple teams and AI agents can work concurrently without editing a shared version file or changelog entry.

## What can be automated?

With Semversioner as the release-intent layer, a CI/CD workflow can automate:

- pull request checks for missing changesets
- semantic version calculation
- release candidate and development versions
- changelog and release-note generation
- package publishing
- container image tagging and publishing
- Git tag and GitHub Release creation
- deployment promotion
- provenance and release metadata
- notifications and downstream dependency updates

## Example AI-native workflow

An AI coding agent completes a task and records the release impact with the code:

```shell
semversioner add-change \
  --type minor \
  --description "Add tool-calling support to the orchestration agent" \
  --attributes pr_id=842 \
  --attributes component=agent-runtime \
  --attributes author_type=ai-agent
```

CI verifies that release intent is present:

```shell
semversioner check
```

After the pull request merges, the release workflow calculates and publishes the release:

```shell
VERSION=$(semversioner next-version)
semversioner release
semversioner changelog > CHANGELOG.md

# Build and publish using $VERSION
```

The same workflow works whether the change was authored by a developer, generated by an AI agent, or created through human and AI collaboration.

## Example GitHub Actions release

```yaml
name: Release

on:
  push:
    branches:
      - main

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install Semversioner
        run: pip install semversioner

      - name: Calculate version
        id: version
        run: echo "value=$(semversioner next-version)" >> "$GITHUB_OUTPUT"

      - name: Create release metadata
        run: |
          semversioner release
          semversioner changelog > CHANGELOG.md

      - name: Build and publish
        run: |
          echo "Publishing version ${{ steps.version.outputs.value }}"
          # Add package, container, or deployment commands here

      - name: Commit release files
        run: |
          git config user.name "release-bot"
          git config user.email "release-bot@users.noreply.github.com"
          git add .semversioner CHANGELOG.md
          git commit -m "Release ${{ steps.version.outputs.value }}"
          git tag "${{ steps.version.outputs.value }}"
          git push origin main --tags
```

For production use, add your own test, security, approval, signing, publishing, and deployment controls around the release steps.

## Semantic Versioning

The [Semantic Versioning](https://semver.org/) specification uses a three-part version number:

```text
<major>.<minor>.<patch>
```

Semversioner follows these guidelines:

- Breaking backward compatibility or major features bump the **major** version.
- New functionality without breaking backward compatibility bumps the **minor** version.
- Bug fixes and miscellaneous changes bump the **patch** version.

An example version is `1.0.0`.

## How it works

At any given time, the `.semversioner/` directory looks like:

```text
.semversioner
├── next-release
│   ├── minor-20181227010225.json
│   └── major-20181228010225.json
├── 1.1.0.json
├── 1.1.1.json
└── 1.1.2.json
```

The release process aggregates everything in `next-release` into a single JSON file for the new version, for example `1.12.0.json`. The released JSON file contains the individual changes that contributed to that version.

This model gives every change an independent release record while preserving a complete history of each published version.

## Usage

Use `--help` on any command to see its available options:

```shell
semversioner --help
```

### Adding changesets

Use the CLI to create a changeset that is committed with your code. This ensures every pull request or commit contains its own change description and version-bump intention.

```shell
semversioner add-change --type patch --description "Fix security vulnerability in authentication"
```

Allowed `--type` values are `major`, `minor`, and `patch`.

You can attach custom attributes that become available to release templates:

```shell
semversioner add-change --type patch \
  --description "Improve token validation" \
  --attributes pr_id=322 \
  --attributes issue_id=123 \
  --attributes component=authentication
```

Custom attributes are useful in AI-native delivery workflows for recording information such as:

- the agent or model that contributed the change
- the owning team or service
- risk classification
- feature flags
- deployment targets
- issue and pull request references

### Checking working-directory status

Check the current version, computed next version, and unreleased changes:

```shell
semversioner status
```

Example output:

```text
Version: 1.0.0
Next version: 1.1.0
Unreleased changes:
    minor: Added new authentication feature
(use "semversioner release" to release the next version)
```

### Enforcing changesets in CI/CD

Use `check` in pull request validation to confirm that unreleased changes exist in `.semversioner/next-release/`:

```shell
semversioner check
```

If no changes are found, the command exits with a non-zero status code and prints an error message.

This creates a simple contract for developers and AI agents: meaningful changes must include explicit release intent before they can merge.

### Releasing a new version

Run `release` from your CI/CD workflow after changes merge to the main branch:

```shell
semversioner release
```

The command automatically computes the version from the unreleased changes, creates the new version JSON file, and clears the `next-release` directory.

### Generating the changelog

Generate a changelog from the structured release history:

```shell
semversioner changelog > CHANGELOG.md
```

#### Customizing the changelog template

Create a Jinja2 template and pass it to the command:

```shell
semversioner changelog --template .semversioner/config/template.j2
```

A basic template:

```jinja2
# Changelog
{% for release in releases %}

## {{ release.version }}
{% for change in release.changes %}
- {{ change.type }}: {{ change.description }}
{% endfor %}
{% endfor %}
```

Custom attributes such as `pr_id`, `issue_id`, `component`, or `author_type` can also be referenced in the template. The `current_version` value is available as well:

```jinja2
# Changelog
Current version: {{ current_version }}

{% for release in releases %}
## {{ release.version }}{{ ' (' + release.created_at.strftime('%Y-%m-%d') + ')' if release.created_at }}

{% for change in release.changes %}
- {{ change.description }}{{ ' [component: ' + change.attributes.component + ']' if change.attributes and change.attributes.component }}
{% endfor %}
{% endfor %}
```

#### Filtering the changelog

Show changes for a specific version:

```shell
semversioner changelog --version "1.0.0"
```

Show changes for the latest released version:

```shell
semversioner changelog --version $(semversioner current-version)
```

### Getting the current version

```shell
semversioner current-version
```

### Getting the next version

Use `next-version` to calculate the upcoming version without modifying files. This is useful for development, release-candidate, package, and container workflows:

```shell
semversioner next-version
```

```shell
semversioner --path /path/to/project release
```
